# Журнал задачи, операции и действия

Читать перед записью прогресса или исправлением частичной цепочки. Содержание: смысл записей → поля → переходы → цепочки → восстановление.

## Смысл записей

Задача задаёт цель и полномочия. Операция описывает один смысловой результат; несколько установок флажков могут быть действиями одной операции выбора. Действие — отдельное исполнение с конкретной целью. Запись журнала не выполняет браузерную команду и не выдаёт разрешение.

Цель, объекты, основание, ожидаемый результат и вывод формирует агент. ID, ревизии и квитанции передаются структурно. Не придумывай доказательства или разрешение ради допуска. Не создавай отдельную операцию для каждого чтения, если это не отдельный смысловой результат; не дроби текст на фиктивные статусы.

## Поля и ограничения

- Новая операция: operation_id, kind, object_ref, authorization_ref, success_criterion, operation_status:planned; object_refs задаёт точные допустимые объекты, если их несколько.
- Новое действие: action_id, action_request_id, kind, action_status:planned и конкретный object_ref из операции. Можно опустить object_ref только при единственной цели операции. desired_state описывает намерение, например checked=true.
- `kind`: inspect — чтение/проверка; navigate — переход; select — выбор; create — создание, включая скачивание; modify — изменение; move — перенос; delete — удаление; submit — отправка. Для новой операции/действия обязателен, для обновления можно опустить; переданный должен совпасть. У задачи create/context/state kind не используется.
- Заметки, включая evidence, до 400 единиц UTF-16. Без секретов, значений форм, текстов сообщений, полных URL и снимков. `WORKFLOW_FIELD_TOO_LONG` сообщает поле и предел; сокращай до существенного факта.
- Идентичность операции/действия не меняй для обхода конфликта. `change:context` обновляет title, goal, scope, authorization_ref вместе с evidence и expected_revision.
- Лимиты текущего журнала: 100 операций, 100 действий на операцию, 500 на задачу; события и квитанции последних записей ограничены отдельно 200 элементами каждое. evidence является полем события, не самостоятельным дополнительным событием. При лимите не удаляй неизвестные исходы.

## Порядок статусов

| Запись | Нормальный путь | Альтернативы |
|---|---|---|
| Операция | planned → running → verified | running → awaiting_verification → verified; допустим возврат awaiting_verification → running |
| Действие | planned → dispatched → verified | При неопределённости: planned/dispatched → unknown; затем verified, deviated или failed по наблюдению |

Новая операция только planned, прямой planned → verified запрещён. Каждый переход существующей операции требует evidence. verified требует совокупного подтверждения результата и завершённых состояний всех её действий. Все действия должны быть терминальными также перед awaiting_verification операции.

dispatched записывается после фактической отправки и только с подходящей dispatch_receipt текущей MCP-сессии/режима. Квитанция подтверждает отправку, не успех. При потере квитанции или перезапуске не выдумывай dispatched: используй unknown и проверку результата. unknown не разрешает повторную отправку. deviated означает наблюдаемый эффект, отличный от ожидаемого, и не даёт права на автоматическое исправление. failed/cancelled выбирай по установленному факту; неизвестный исход не превращай в failed ради закрытия задачи.

Терминальные статусы не возобновляются. Задача paused запрещает новые планы/отправку, но позволяет фиксировать результаты прежних действий. Завершение задачи требует терминальных операций. Служебное состояние журнала не заменяет остановку браузера или внешнего агента.

## Серии и журнал

prepare_operation/execute_operation исполняют браузерную серию, но не создают записи смыслового журнала. Планируй одну операцию и действия по объектам; для шага используй action_request_id = plan_id + "_" + step.id. После исполнения квитанция steps[].dispatch_receipt подтверждает отправку только своего шага. Результаты проверяй по состояниям и общему критерию операции.

already_satisfied означает, что ввод не понадобился: не записывай dispatched. Если действие уже запланировано, cancelled с объяснением «желаемое состояние уже установлено» сохраняет факт отсутствия ввода; общий результат операции подтверждается отдельным evidence. unknown остаётся неизвестным до наблюдения. Для оставшихся planned/not_sent не выдумывай отправку. Сначала заверши установление исходов, затем решай о новом плане.

## Цепочки и ревизии

Используй последнюю подтверждённую ревизию. При возобновлении или сомнении — `get_task_progress`; после успешной записи не требуется дополнительное чтение только ради ревизии.

`record_task_progress_chain` принимает одну задачу, начальную expected_revision и 1–20 steps с уникальными устойчивыми request_id без собственных ревизий. Он передаёт фактическую ревизию между шагами и останавливается на первом отказе. Цепочка не атомарна: прежние успешные записи сохраняются.

Объединяй только записи с уже известными основаниями: план и реальное начало можно записать вместе; успешное завершение браузерного действия — только после наблюдения. Не ставь в одну заранее отправленную цепочку будущие результаты браузерных действий.

## Восстановление записи

После отказа прочитай failed_step, committed_steps, last_confirmed_revision и при необходимости `get_task_progress`. После потерянного ответа или `WORKFLOW_CHAIN_REPLAY_REQUIRES_INSPECTION` не повторяй всю цепочку. Продолжай неприменённые записи с их прежними ID; при неизвестном результате записи сохраняй идентичные аргументы для документированной сверки. Исправленный, подтверждённо отклонённый запрос — новое намерение записи, не подмена успешной квитанции.

Пример: planned сохранился, ошибочный переход сразу к verified отклонён. Если работа действительно уже выполнена и проверена, после чтения журнала запиши running → verified с правдивым evidence о запоздалой записи. Не выполняй действие на сайте повторно ради журнала. Если работа не сделана, сначала выполни её обычным порядком.

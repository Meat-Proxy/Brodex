# Публикация выпуска

Версия хранится в package.json, extension/manifest.json (version и version_name), extension/VERSION.txt и соответствующем теге Git. README и инструкция установки описывают постоянный процесс. Исторические номера допустимы в условиях миграции и отчётах тестов.

1. Обнови код и docs/release-notes.md: изменения, проверка, ограничения, миграция. Не включай локальные конфигурации, данные страниц и результаты тестов.
2. Выполни `node scripts/version.cjs set X.Y.Z`, затем `node scripts/version.cjs check`. Запусти проверки, соответствующие изменению; при изменении установщика проверь tests/install.ps1 в Windows PowerShell и PowerShell в изолированной среде.
3. Проверь diff, создай коммит и отправь main. Создай новый аннотированный тег `vX.Y.Z` на этом коммите и отправь его. Опубликованные теги не перемещай.
4. GitHub Actions проверяет версии, идентичность и bootstrap, затем создаёт **Pre-release** с описанием из того же коммита. ZIP исходников GitHub формирует для этого тега. Предварительный статус сохраняется намеренно, пока проект экспериментальный.
5. Дождись успешного workflow и проверь сам Release: правильный тег, описание, доступный архив и INSTALL-CODEX.md внутри. Тег без Release не считается завершённой публикацией. При отказе публикации устрани причину и повтори workflow; не объявляй выпуск готовым заранее.

Установщики выбирают самый новый опубликованный Release по published_at, включая предварительные. Ссылка /releases/latest для этого не подходит. Ветка main используется только по явному запросу разработки.

Автоматизация использует встроенный GITHUB_TOKEN с contents: write только у задачи публикации. Личные токены и секреты не требуются. См. [GitHub CLI в Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-github-cli).
